# Project Agent Brief — Hard Rules (C, MuJoCo, Renoir IPC)

These rules apply to every coding agent working in this repo, regardless of
what a task instruction asks for. If a task conflicts with this file, stop
and flag it — do not resolve the conflict silently.

## 1. Toolchain

- Format: `clang-format` (project `.clang-format` if present, otherwise the
  style already used in `src/`/`include/`), run on every touched file
- Static analysis: `clang-tidy` via `cmake --build build --target lint`
  (already configured with `--warnings-as-errors=*` in `CMakeLists.txt`),
  plus `cppcheck --enable=all --inconclusive`; zero new warnings
- Compiler flags always on (already set in `CMakeLists.txt`, do not weaken
  them): `-Wall -Wextra -Wpedantic -Werror -Wshadow -Wconversion
  -Wsign-conversion -Wnull-dereference -Wformat=2 -fstack-protector-strong`
- Dynamic analysis: build and run with ASan+UBSan
  (`./run.sh analyze --headless --duration N`) for any change touching
  memory, sensor buffers, or the transport/foxglove layers; ThreadSanitizer
  (`./run.sh analyze-tsan --headless --duration N`) for any change touching
  the Foxglove bridge thread, shared `sim_t` state, or anything else
  crossing a thread boundary
- Leak checks: `valgrind --leak-check=full --show-leak-kinds=all
  --error-exitcode=1` on any change to malloc/free paths (camera buffers,
  Foxglove bridge buffers, WS frame handling)
- Manual smoke test: `./run.sh all --headless --duration 10` must run
  clean; if the change touches the Foxglove bridge or transport,
  additionally exercise `test_ws_client.py` against a running instance and
  confirm the expected channels/messages arrive
- Profiling: `perf record`/`perf report` for hotspots on the sim-step loop,
  sensor synthesis, or camera rendering path
- If a tool is missing or fails to run, say so explicitly — never fabricate
  a clean result

**Renoir boundary.** This repo consumes Renoir (`../renoir`) purely through
its C API (`target/include/renoir.h`, generated by cbindgen — never the
stale hand-maintained `include/renoir.h` inside the Renoir repo; see
`../renoir/.ai/analysis.md` §7 for why). Do not vendor, patch, or work
around Renoir source from this repo. If a bug or missing feature in Renoir
is blocking work here, record it as a finding (this repo's `.ai/analysis.md`
already cross-references `../renoir/.ai/analysis.md` and `.ai/plan.md` for
issues that belong upstream) and coordinate the actual fix in the Renoir
repo rather than working around it locally.

## 2. Coding standards — priority order when they conflict
1. Memory safety and security (leaks, UB, overflow, injection, untrusted
   network input) — always wins. Note: the Foxglove WebSocket server listens
   unauthenticated on `0.0.0.0` by default — treat all data received over
   that socket as untrusted/hostile input, not just malformed input.
2. MISRA C:2012, then CERT C Secure Coding Standard
3. Everything else — general readability and idiom

Non-negotiable regardless of guide cited:
- No raw `malloc`/`calloc`/`realloc` without a matching, auditable free path
  — every allocation's owner and free site should be traceable by reading
  the code, the way `sensor_cleanup`/`foxglove_destroy` already do
- No `gets`, `strcpy`, `sprintf`, `strcat` (use bounded variants —
  `snprintf` is already the house style throughout this codebase)
- No implicit int/pointer conversions; every `malloc`/`calloc` result
  checked for `NULL` before use (already consistent practice here — keep it)
- Any function that parses bytes received over the network (WebSocket
  frames, client JSON messages) must validate lengths/bounds before
  indexing or copying — never trust a client-declared length without a
  sanity ceiling
- Sizes and buffers that cross the transport/Renoir boundary
  (`transport_advertise`/`transport_publish`/`transport_read_next`) must
  stay consistent between the publish side and any subscribe side for the
  same topic name — Renoir will not detect or reject a mismatch (see
  `../renoir/.ai/analysis.md` §11.1); this repo is responsible for keeping
  its own topic sizing consistent

## 3. Mandatory checks before any step is "done"
- [ ] `clang-format` applied to every touched file
- [ ] `clang-tidy` lint target run, zero new warnings, real output logged
- [ ] `cppcheck --enable=all --inconclusive` run, zero new findings
- [ ] Headless smoke run (`./run.sh all --headless --duration N` or
      equivalent direct `./hummingbird` invocation) completed successfully,
      real output logged
- [ ] ASan+UBSan run (`./run.sh analyze`) on any change touching memory,
      sensor buffers, or transport/Foxglove code, real output logged
- [ ] TSan run (`./run.sh analyze-tsan`) on any change touching the
      Foxglove bridge thread or shared state, real output logged
- [ ] `test_ws_client.py` run against a live instance if the change touches
      the Foxglove protocol/serialization/bridge layer
- [ ] Benchmark/perf comparison if a hot path (sim step, sensor synthesis,
      camera render, bridge broadcast loop) was touched

## 4. Comments policy
- The agent does **not** add code comments, docstrings, or inline
  explanations under any circumstances unless the user explicitly
  authorizes it for that specific change. Silence on this means: no
  comments.
- This includes not adding "explaining" comments to justify tricky pointer
  arithmetic, buffer sizing, or thread-safety reasoning — put that
  explanation in the implementation log instead.
- Never restate what code does; if authorized, comment only genuinely
  non-obvious *why* (the existing `mixer()` and `viewer_loop`'s
  `mjr_setBuffer` comments in this repo are the right calibration — a
  hidden invariant or workaround, not a restatement).

## 5. Version control
- Only push when directed by user.
- Always open a Pull Request for review — never merge automatically, never
  force-push.
- **Never commit anything under `.ai/`** — it is planning/log scratch
  space, not part of the shipped project. Ensure `.ai/` is listed in
  `.gitignore` (already done); do not add or commit any other `.ai/*` file.
- Commits use whatever git identity (`user.name`/`user.email`) is already
  configured in this repo/machine — typically the user's GitHub no-reply
  address (`<id>+<username>@users.noreply.github.com`). Never set,
  override, or append to author/committer identity. If no identity is
  configured, stop and ask rather than inventing one.
- **No mention of any AI agent, model, or tool anywhere** — not in commit
  messages, not in a `Co-Authored-By:` trailer, not in code comments (see
  §4), not in the PR title or description, not in `.ai/` files that get
  referenced in a commit message. Commit messages describe the change only,
  in Conventional Commit format: `<type>(<scope>): <summary>`.

## 6. Scope control
- Touch only the files listed for the current step in `.ai/plan.md`.
- No opportunistic refactors, renames, or dependency bumps outside task
  scope.
- Never delete or weaken a compiler warning flag, sanitizer flag, lint
  rule, or the CI matrix to make things pass.
- If reality diverges from the plan mid-implementation, stop and add a
  "Plan amendment" section to `.ai/plan.md` rather than improvising.
- Hard cap per step: ~150 changed lines or 5 touched files — over that,
  stop and ask before continuing.
- Never add a new dependency (including bumping the required MuJoCo or
  Renoir version) without flagging it first.

## 7. Anti-hallucination rules
- Never call a Renoir FFI function, MuJoCo API, GLFW function, or any
  other external symbol not verified to exist — check
  `target/include/renoir.h` (or `../renoir/src/ffi/` if the generated
  header is unavailable), the MuJoCo header, or the relevant library docs
  before using it.
- Never report a build/lint/sanitizer/test/benchmark result not actually
  executed this session.
- When unsure about compiler/toolchain/Renoir-ABI behavior, check it
  directly rather than inferring from training data.
- Cite real file paths and line numbers.
- If a tool is missing or a command fails, say so plainly instead of
  producing a plausible-looking fake result.

## 8. Workflow
1. Task defined in `.ai/task.md`.
2. Plan written to `.ai/plan.md` (no code changes at this stage).
3. Implementation happens in source files only, one plan step at a time,
   with the checks in §3 run and logged to `.ai/implementation-log.md`.
4. Independent review re-runs §3's checks and writes `.ai/code-review.md`
   and `.ai/verification.md` with a pass/fail verdict per acceptance
   criterion.
5. Failures route back to implementation. Loop until verification passes,
   then open a PR (§5) — do not merge it.
